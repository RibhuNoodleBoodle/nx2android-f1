2. DEFINE EXACTLY WHAT 'CUSTOM DRIVERS' COULD MEAN
==============================
Investigate the following separately. Do NOT conflate them:
A. User-selectable ANDROID USER-SPACE VULKAN drivers (for example, compatible Mesa Turnip builds on supported Qualcomm Adreno GPUs).
B. A bundled or separately supplied compatible user-space Vulkan driver selected per game or per generated APK.
C. A driver loaded through an Android-native mechanism, if supported (for example, libadrenotools or another well-documented method); do not assume such integration is appropriate without examining API compatibility, licensing, and the project's execution model.
D. Android's standard Vulkan loader / system driver selection and any debug-layer or external-driver mechanisms, clearly distinguishing layers from ICDs/drivers.
E. Unsupported ambitions such as installing/replacing kernel GPU drivers from an unprivileged APK; explain precisely when root, OS privileges, matching kernel components, or firmware would be needed.

Do not assume rootless custom Vulkan driver loading is possible on every Android version, GPU, or runtime. Specifically evaluate:
- ARM64 ABI and Android API/NDK requirements.
- Vulkan loader and dispatch mechanism; function-pointer ownership and proc-address resolution; whether a custom loader needs to handle all instance/device function resolution and extensions.
- Android linker namespaces and permitted native-library paths; library dependency chains, versioned symbols, and whether arbitrary driver shared objects can be loaded from application storage on relevant OS versions.
- Correctness across activity lifecycle, Surface/ANativeWindow, swapchain creation and recreation, native memory sharing, presentation, synchronization, and app sandboxing.
- Vulkan API level, required extensions/features, descriptor/rendering capabilities, shader capabilities, texture compression, memory allocation, and possible compatibility workarounds.
- Snapdragon/Adreno feasibility versus Xclipse, Mali, PowerVR and any other GPU families; distinguish driver-loading feasibility from actual game rendering support.
- Security risks of arbitrary .so execution, unsafe driver archives, path traversal, dependency substitution, tampered libraries, crashes, denial of service, integrity checks and untrusted inputs.
- Binary distribution and licensing (Mesa, third-party loaders and upstream licenses); distinguish 'can load an externally supplied driver' from 'can legally package and redistribute a specific binary'. Do not tell Gemini to obtain proprietary or unauthorized binaries.
- Risks to existing supported games and devices; graceful compatibility fallback and recovery when a selected custom driver cannot load or initialize.

Remember nx2android is a game-porting/compatibility project, NOT a conventional multi-game Android emulator. Evaluate how any driver-selection feature must survive its generated per-game APK pipeline. Verify this from code before designing the integration.
